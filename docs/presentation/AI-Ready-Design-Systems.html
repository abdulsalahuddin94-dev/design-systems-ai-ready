⭐Setup / ➜ The problem
Why this exists

Most design systems are made for people to look at. AI agents need to read them.

What an AI agent sees today

  • Hard-coded hex values and font sizes on the canvas
  • Detached components and default layer names like Frame 124
  • No written rule for when to use which component
  • Light and Dark drawn twice instead of switched by modes
fill: #299B48 // which green? primary? success?
Frame 124 › Rectangle 23

What this workflow produces

  • Every value is a variable: Primitives, then Semantics with Light and Dark
  • Every component is built from smaller components, with Auto Layout
  • Every component carries Purpose, Usage Rules and Accessibility in its description
  • An audit proves nothing is unbound or detached

Scenarios

One intake, every starting point

A

New from scratch

Brand color and font in, full system out: tokens, components, docs, Storybook.

Extract from screens

Reads unstructured UI, pulls colors, type and spacing, maps them to variables.

C

Refactor an existing DS

Variable map with confidence, fixes unlinked screens, flattens alpha colors by OKLCH match.

⭐Setup / ➜ How it works
The pipeline

The agent builds. A person approves each checkpoint.

Step 1

Intake

Arrow-key questions: platform, path, brand, modes, RTL, icons. Reads the Inputs folder first.

Step 2

Foundation

Primitives, Semantics (Light/Dark), spacing, radius, type, text and effect styles. Linked docs pages.

✓ Checkpoint 1
Step 3

Components

Atoms, then Molecules, Organisms, Patterns. Published as a library.

✓ Checkpoint 2
Step 4

Screens

Spec approved first, then built only from DS components, compared side by side.

✓ Checkpoint 3
Step 5

Audit

Unbound tokens, raw values, detached components, contrast, default names.

Step 6

Docs

Project skills, component registry and a live Storybook with names that match Figma.

One session per phaseNo agent approves its own checkpointEvery fixed mistake becomes a ruleCHANGELOG per project

⭐Setup / ➜ Methods
Rules the agent cannot skip

Strict tokens, strict Atomic Design

Two token tiers, in this order

brand/500 = #3352D6 // Primitive: raw value
color/action/primary → brand/500 // Light
color/action/primary → brand/300 // Dark
Button.fill = color/action/primary

Then spacing, radius and typography variables, then text and effect styles, then components. Docs pages are bound to the variables, so they never go stale.

Never build a tier before the one below it

Atoms

Button, Checkbox, Badge, Icon, Avatar

Molecules

Input Field, Search Bar, List Item

Organisms

Top Bar, Nav Bar, Cards

Patterns

Sign Up Form, OTP, Lists

Variant, State, Size and Icon are properties, never separate components. Nested properties are exposed at the top. Icons are real instances with a swap property.
